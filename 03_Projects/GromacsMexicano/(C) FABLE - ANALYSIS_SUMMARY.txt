2. RACE CONDITION ANALYSIS

   FORCES ARRAY f[i][x] — CRITICAL
   ────────────────────────────────
   Problem: Multiple bonds may reference same atom i → concurrent writes
   
   Example:
     Bond A: (atom 1 -- atom 5) updates f[1] and f[5]
     Bond B: (atom 1 -- atom 2) updates f[1] and f[2]  ← RACE on f[1]
   
   Solution A (RECOMMENDED): Force buffering
     - Each thread gets private buffer f_thread[n_atoms][3]
     - Compute forces into private buffer (no race)
     - After parallel loop: sequential reduction to global f[]
     - Overhead: ~5% memory, ~5% compute (small buffer writes)
     - Best for: Small n_bonds (< 1000)
   
   Solution B (ALTERNATIVE): Atomic operations
     - #pragma omp atomic on each force component update
     - Simpler code, but serializes writes to shared locations
     - Overhead: ~10–20% (atomic operations expensive)
     - Best for: Very uneven load (scheduler can hide latency)
   
   PRESSURE TENSOR P[3][3] — MANAGEABLE
   ────────────────────────────────────
   Problem: All threads accumulating into same 3×3 matrix
   Solution: #pragma omp reduction(+:P[3][3]) — standard in OpenMP 4.5+
   Overhead: Negligible (hardware supports 3×3 reduction efficiently)
   Risk: LOW (if OpenMP 4.5+ available; GCC 6.0+, Clang 4.0+)

3. FLOATING-POINT SENSITIVITY

   Issue: Parallel reduction sums in different order than serial
   ├─ Serial: E = a + b + c + d + e
   └─ Parallel (4 threads): E = (a+b) + (c+d) + e  [different order]
   
   Result: ΔE ≈ 1e-10 (FP rounding error)
   
   Physics gate: ±0.01 kJ/mol/atom → well above this noise
   Validation: Test with OMP_NUM_THREADS=1 must match reference
   Mitigation: Already planned in project physics validation

4. LOAD BALANCING

   Bonded forces: UNEVEN WORK PER ITERATION
   ├─ Bonds: uniform (same distance calculation)
   ├─ Angles: ~10× more expensive than bonds (includes trig)
   └─ Dihedrals: ~50× more expensive (includes dihedral angle + trig)
   
   Solution: #pragma omp parallel for schedule(guided, chunk_size)
   ├─ Dynamic work stealing (fast tasks don't starve slow ones)
   ├─ Tuning: chunk_size = 8–32 (benchmark to find optimal)
   └─ Expected: 90–95% thread utilization even with 50× variance

   Integrator loops: PERFECTLY UNIFORM
   └─ Solution: #pragma omp parallel for schedule(static)
   └─ Reason: Predictable load, no dynamic adjustment needed, better cache

================================================================================

Typical MD timestep (water+NaCl, 2544 atoms):
  Bonded forces:        ~0.5 ms  → 4–6× with OpenMP
  Integrator updates:   ~0.2 ms  → 3–4× with OpenMP
  Ewald reciprocal:     ~1.0 ms  (GPU, not parallelized)
  Non-bonded forces:    ~2–4 ms  (GPU, not parallelized)
  I/O:                  ~0.1 ms  (serial, negligible)
  ─────────────────────────────
  Total:                ~3–5 ms

With full OpenMP (Phases 1+2):
  Bonded forces:        ~0.1 ms  (6× speedup)
  Integrator:           ~0.05 ms (4× speedup)
  Ewald/non-bonded:     ~2–4 ms  (unchanged, GPU)
  ─────────────────────────────
  Total:                ~2.2–4.2 ms → ~1.3–1.5× overall

Note: GPU dominates (~40% of total time), limiting overall speedup to ~1.5× even
with perfect CPU parallelization. Full benefit realized when GPU unavailable or
for CPU-heavy workloads (e.g., production runs with CPU thermostat/barostat).

RISKS & MITIGATIONS
================================================================================

Risk 1: Race condition on force array → data corruption
  Severity: CRITICAL
  Mitigation: Force buffering (private per-thread) + sequential reduction
  Verification: Deterministic forces with OMP_NUM_THREADS=2,4,8

Risk 2: Floating-point reduction order → ΔE variation
  Severity: MEDIUM
  Mitigation: Physics gate tolerance (±0.01 kJ/mol, well above 1e-10 error)
  Verification: Compare OMP_NUM_THREADS=1 vs. reference (bit-identical)

Risk 3: Uneven load → thread starvation
  Severity: LOW (dihedrals 50× more expensive than bonds, parallelizable)
  Mitigation: schedule(guided, chunk_size) for dynamic balancing
  Verification: Profile with vtune/perf (check thread utilization)

Risk 4: Cache coherency (false sharing on virial matrix)
  Severity: LOW
  Mitigation: Reduction clause handles cache coherency automatically
  Verification: Micro-benchmark P[3][3] reduction performance

Risk 5: Compiler/OpenMP version incompatibility
  Severity: MEDIUM
  Mitigation: Require OpenMP 4.5+ (GCC 6.0+, Clang 4.0+)
            Fallback: manual reduction for older compilers (less efficient)
  Verification: cmake check + compile-time assertion
